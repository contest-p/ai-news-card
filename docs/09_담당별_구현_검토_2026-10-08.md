# 담당별 PRD 대비 구현 검토 — 2026-10-08

기준: 공통 PRD 본문 v0.4, 개인 PRD 본문 v0.3. 현재 로컬 저장소 코드와 기록을 검토했다. 담당자의 저장소 밖 작업이나 배포 상태는 평가에 포함하지 않았다. 소스 코드는 수정하지 않았다.

## 판단

## 우선 수정/완료할 항목

### 1. [P1] 오래된 해제 요청이 새 구독을 해제한다

- 근거: backend/main.py:522–534, frontend/app.js:219–225.
- 현재 해제 요청에는 subscription_id가 없고 서버는 uid의 현재 문서를 찾는다.
- 재현: 구독 A 생성 → A 해제 → 구독 B 생성 → A 화면에서 보낸 형태의 해제 요청 재전송. 200 응답으로 B가 cancelled가 된다.
- 공통 PRD 10-3은 이전 구독 ID로 새 구독을 해제할 수 없어야 한다고 명시한다.
- 조치: 프런트가 확인 중인 구독 ID와 confirm을 보내고 서버 트랜잭션에서 동일 ID인지 검사. 반복된 A 요청은 B에 영향을 주지 않아야 한다.
- 담당: Backend, Frontend.

### 2. [P1] 설정·동의 없는 요청도 활성 구독으로 저장한다

- 근거: backend/main.py:212–219, 402–418, 443–457.
- 재현: 인증한 사용자로 POST /subscriptions/save에 {"plan":"basic"}만 전송하면 200, status=active. start_date와 agreed_privacy는 없다.
- engine_settings가 선택적이고 기존 입력도 모두 없으면 검증을 건너뛴다. 반복 요청은 날짜 없는 활성 구독을 다시 덮어쓸 수도 있다.
- 결과: 성공으로 표시한 구독을 엔진은 불완전 설정으로 제외한다. 필수 동의·발송 설정을 서버에서 강제하지 않는다.
- 조치: 유효한 구독 설정과 최신 동의 버전을 필수로 요구하고, 동의 시각을 저장. 레거시 입력을 지원해도 동일 정책을 적용.
- 담당: Backend.

### 3. [P1] 폐기된 토큰·비활성 사용자 검사가 빠져 있다

- 근거: backend/main.py:166–174. auth.verify_id_token(token) 호출에 check_revoked=True가 없다.
- 공통 PRD 5절은 토큰 폐기와 사용자 비활성 상태까지 확인하도록 요구한다.
- 결과: 관리자 비활성/토큰 폐기 이후에도 기존 ID 토큰의 유효기간 동안 보호 API 사용을 차단하지 못할 수 있다.
- 조치: 폐기/비활성 검사를 활성화하고 해당 오류의 401 처리 및 회귀 테스트 추가.
- 담당: Backend.

### 4. [P1] 실제 연결 배치는 항상 과거 근거 없음으로 처리한다

- 근거: engine/card_builder.py:17–31, engine/tools/connected_batch.py:107–109.
- 로컬 RAG 모듈과 테스트는 있지만 연결 도구에서 search_evidence를 주입하지 않아 no_evidence_search가 실행된다. 과거 기사가 DB에 있어도 검색하지 않는다.
- FirestoreArticleRepository는 기사 저장을 제공하지만 벡터 저장·검색은 연결되지 않았다. 연결 수집 단계도 임베딩을 생성하지 않는다.
- 결과: 현재 연결 경로는 카드 1만 생성하며, 필수 RAG 사용 증거와 배경 카드의 실제 서비스 흐름을 충족하지 못한다.
- 조치: 임베딩 저장·재처리, 날짜/분야 조건의 벡터 검색, 출처 메타데이터를 연결하고 실제 과거 기사로 카드 2 생성 사례를 기록.
- 담당: 리드, Backend 인덱스/IAM 리뷰, QA 관련성 평가.

### 5. [P1] 전체 구독의 정기 자동 발송이 연결되지 않았다

- 근거: .github/workflows가 없고, engine/tools/connected_batch.py:45–46, 95–129는 지정한 테스트 구독만 처리한다.
- 테스트 도구는 만료 목록을 빈 배열로 반환한다. 일반 배치 함수의 종료 안내 구현과 실제 운영 진입점은 구분해야 한다.
- 결과: 가입 이후 자동 일일 브리핑과 자연 만료 안내가 돌아가는 운영 경로가 저장소에 없다.
- 조치: 전체 대상과 종료 안내를 처리하는 운영 진입점·매시간 7분 Actions 예약·인증/Secrets·실행 요약/복구를 연결.
- 담당: 리드, 배포·QA.

### 6. [P1] 30일 개인정보 정리와 실제 삭제 요청 경로가 없다

- 근거: engine/batch.py:47, 81–88, engine/tools/connected_batch.py:129, engine/firestore_runtime_store.py:163–205, frontend/app.js:133.
- 배치에는 정리 콜백 자리만 있고 연결된 도구는 전달하지 않는다. Backend에는 요청 처리/정리 구현이 없으며 프런트는 요청 채널을 나중에 연결하겠다는 문구만 표시한다.
- MIME의 expires_at은 복원 차단일 뿐 실제 삭제가 아니다. chunks에는 주소와 피드백 토큰을 포함한 MIME이 남는다.
- 결과: 웹의 30일 삭제/익명화 안내를 현재 코드가 이행하지 못하고, 전용 삭제 화면을 생략할 때 필요한 수동 채널도 없다.
- 조치: 사용자·구독·스냅샷·피드백 토큰·발송 기록·MIME 부모/chunks·Auth 계정의 보관/삭제 범위를 정하고 재실행 가능한 정리와 실제 본인 확인 요청 채널 제공.
- 담당: Backend 정책/로직, 리드 호출 연결, Frontend 안내, QA 검증.

### 7. [P1] 메일 피드백 링크가 저장 API까지 연결되지 않는다

- 근거: backend/main.py:346, 545–580, frontend/app.js:234–237.
- 엔진은 토큰을 발급받아 링크를 넣지만 catalog는 feedback=false다. 프런트의 /feedback/resolve와 /feedback POST 경로가 서버에 없다.
- 기존 /feedback/save는 로그인과 1–5점 평가를 요구하며 fragment 토큰/up/down 계약과 다르다. 구독 문서 ID도 uid인데 조회에 subscription_id를 사용해 새 구독 응답 ID로 호출하면 404가 된다.
- 결과: 받은 메일의 평가 링크는 준비 중 안내로 끝난다.
- 조치: 토큰 해시 조회·만료·사용자 삭제 확인·POST resolve/확정 저장을 연결. 링크 진입만으로 평가가 저장되지 않는 기존 프런트 원칙은 유지.
- 담당: Backend, Frontend, QA 실제 링크 확인.

### 8. [P1] 검증된 공개 분야 목록이 아닌 전체 여섯 분야를 제공한다

- 근거: backend/main.py:340–346, backend/engine_api.py:20–38, deployment-qa/rss_validator/rss_check.py:10–44.
- catalog와 서버 입력 검증은 여섯 분야를 고정 제공한다. QA 검사는 RSS 파싱·기사 개수·첫 기사 분류만 보고 통과 처리한다. 게시 시각·본문 추출·이용 조건·분야별 공개 승인과 연결되지 않았다.
- 결과: PRD의 공개 조건을 충족하지 않은 분야도 가입할 수 있다. 현재 기록만으로 분야별 두 언론사 목표 또는 한 곳 공개의 승인/한계 고지를 확인할 수 없다.
- 조치: 공개 승인 목록을 단일 설정으로 관리하고 catalog와 구독 검증에 함께 적용. 본문/날짜/조건/분야 표본과 공개 판단을 기록.
- 담당: QA 검증, 리드 범위 결정, Backend 적용.

### 9. [P1] 활성 구독의 다음 날 설정 변경 기능이 없다

- 근거: backend/main.py:346, frontend/app.js:144, frontend/README.md.
- settings_change=false이며 웹은 준비 중 문구를 표시한다. 변경 API·현재/다음 설정·버전 충돌 처리도 없다.
- 조치: 오늘 작업은 고정하고 다음 KST 날짜부터 적용하는 설정 버전/스냅샷·API·화면을 함께 구현. 기간 중간 연장은 제외.
- 담당: Backend, Frontend, 리드 스냅샷 협업.

### 10. [P2] QA 결과와 배포 변경 합의 기록이 부족하다

- deployment-qa에는 RSS 검사 결과와 배포 안내가 있다. 통합·장애·권한·RAG 라벨·5명 실사용 설문·수정/재확인 기록은 없다.
- engine/docs/CARD_RENDER.md에는 실제 이미지와 메일 검수 기록이 있으므로 메일 QA 전체가 없다고 판단하지 않는다. 이번 검토에서 실제 외부 서비스 상태를 재검증한 것은 아니다.
- deployment-qa/VERCEL_LOGIN_DEPLOY.md는 Backend를 Vercel에 배포하도록 안내하지만 공통/개인 PRD는 Render로 고정한다. 변경 승인과 PRD 갱신 기록을 저장소에서 확인하지 못했다.
- 조치: 검증 결과를 환경·날짜·재현 방법·증거와 함께 모으고 배포 스택 변경 여부를 문서에 명시. 실제 확인 없는 항목을 완료로 표시하지 않기.
- 담당: 배포·QA, 리드 문서 취합.

## 검증 결과와 한계

- Frontend: 기존 Node 테스트 15개 통과.
- Backend: 기존 unittest 24개 통과.
- Engine: 기존 unittest 236개 통과.
- 합계 275개 통과. 메모리 DB 추가 재현에서 위 1·2번 결함을 확인했다.
- 문서에 적힌 backend/.venv와 engine/.venv가 현재 체크아웃에 없어 별도 임시 Python 3.12 환경으로 실행했다. 필요한 패키지를 설치했으며 모든 전이 의존성을 저장소 lock과 똑같이 맞춘 실행은 아니다.
- 테스트에는 외부 API/DB/SMTP 대역이 포함된다. 이번 검토는 실제 메일 발송·배포 변경·Google 로그인·모델 다운로드/실제 E5 평가를 수행하지 않았다.
- 따라서 자동 테스트 통과를 공개 테스트·배포 완료의 증거로 사용하면 안 된다. 현재 테스트는 미구현 기능을 준비 중으로 표시하는 동작도 통과시킨다.
- 검토 중 소스 코드와 배포 설정은 변경하지 않았다. 이 검토 문서만 추가했다.
