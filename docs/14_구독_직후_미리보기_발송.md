# 구독 직후 첫 미리보기 발송

구독 신청은 다음 날부터의 정기 발송 일정과 별도로 첫 미리보기를 요청한다. 구독 저장 트랜잭션에서 `preview_requested_at`, 최초 선택 설정인 `preview_settings`, `preview_dispatch_status=pending`을 함께 저장한다.

저장 후 백엔드가 GitHub `engine-mail.yml`의 workflow_dispatch를 호출한다. 입력은 `mode=run`, `delivery_at=""`, `preview_subscription_id=<저장된 구독 ID>`다. 호출은 최대 8초까지 기다리고, 실패해도 구독 저장을 되돌리지 않는다. 같은 신청 요청 키의 재시도는 같은 구독과 작업 ID를 사용한다. dispatch 승인 상태가 이미 accepted면 다시 호출하지 않는다.

Actions는 해당 구독의 `subscription_preview` 작업만 처리한다. 환경 준비와 실제 기사 수집 후 선택 분야·키워드에 맞춰 개인별 카드와 메일을 만든다. 정기 예약의 정각 대기를 사용하지 않는다. 서로 다른 구독의 미리보기와 정기 배치는 별도 concurrency group을 사용하고, 같은 구독의 중복 전송은 기존 Firestore 선점·고정 작업 ID로 막는다.

메일에는 첫 정기 발송 날짜·한국 시간과 "이런 뉴스 브리핑을 보내드릴게요" 안내를 넣는다. 관심 분야에 새 기사가 없으면 구독 완료 안내를 먼저 보낸다. 기사 수집·AI 생성 자체의 오류는 뉴스 없음으로 처리하지 않고 실패로 기록한다. SMTP 직전에 해제·삭제·만료 여부를 다시 확인한다.

## 배포 설정

백엔드 Vercel 프로젝트의 Production 환경변수에 `GITHUB_PREVIEW_DISPATCH_TOKEN`을 등록한다. 토큰은 `contest-p/ai-news-card` 저장소의 Actions 읽기·쓰기 권한만 필요하다(필수 Metadata 읽기 포함). 사용자 이메일, Firebase 인증 토큰, SMTP·AI 비밀 키는 GitHub dispatch 입력으로 보내지 않는다. 토큰은 프론트나 Git에 넣지 않는다.

백엔드 새 환경변수를 포함해 재배포한 뒤 엔진 workflow와 프론트를 배포한다. 환경변수가 없으면 구독은 저장되고 응답의 `preview_dispatch_status`는 `not_configured`가 된다. 이때 즉시 Actions 호출은 하지 않는다.

정기 배치는 최근 24시간 내의 미리보기 요청도 함께 조회하므로 호출 장애나 재시도 가능한 발송 실패를 복구한다. 미리보기 기한은 신청 시각부터 24시간이며 정기 첫 발송일을 앞당기지 않는다. 첫 미리보기에 사용된 기사도 기존 중복 기사 정책에 포함된다.

## Firebase 확인

- `subscriptions`: `preview_requested_at`, `preview_dispatch_status`, `preview_dispatch_at`. accepted는 GitHub 요청 수락이며 실제 메일 발송 완료가 아니다.
- `engine_delivery_jobs`: 해당 `subscription_id`, `mail_kind=subscription_preview`, `status`, `sent_at`, `error_code`.
- 같은 구독의 정기 작업은 `mail_kind=daily_briefing`으로 구분된다.

## 검증과 한계

구독 저장·다음 날 시작 유지, 분야 설정 보존, dispatch 입력·중복 호출 방지, 실패 후 구독 보존, 신청 당일 대상 조회, 지정 구독만 처리, 선점·SMTP 재실행 중복 방지, 기사 없는 안내, 해제·삭제 차단 및 프론트 문구를 외부 서비스 대역으로 검증한다.

Actions 실행 대기와 환경 준비 때문에 신청 후 수 분이 걸릴 수 있다. 자동 미리보기 메일 수신은 배포·서버 토큰 등록 후 실제 계정으로 신규 구독하여 확인해야 한다. 기존 구독에는 미리보기 요청을 자동 추가하지 않는다.
